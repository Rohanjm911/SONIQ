# SONIQ

## Pure Sound. Infinite Possibilities.

### ROLE AND OBJECTIVE

Act as a senior C++ software architect, cross-platform desktop application developer, audio-engine engineer, digital signal processing specialist, Qt/QML UI engineer, and software testing engineer.

Your task is to design, develop, test, and prepare a complete desktop music player named SONIQ.

SONIQ must be a premium, offline-first, cross-platform music player for Windows, Linux, and macOS. It should combine extensive audio-format compatibility, audiophile-oriented playback, powerful music library management, advanced DSP, optional online music metadata, and a polished desktop interface.

This must be a real, maintainable software application, not merely a UI prototype or a collection of mock screens.

Build actual functionality incrementally. Compile the application, execute tests, investigate failures, and fix problems before declaring features complete.

Do not fabricate functionality, test results, audio capabilities, benchmark numbers, or supported-platform claims.

---

# 1. PRODUCT VISION

Create a music player that offers:

* Extensive practical audio-format support.
* High-quality audio decoding and playback.
* Bit-perfect playback where the entire output path supports and verifies it.
* Advanced audio configuration and DSP.
* Efficient management of large local music libraries.
* Playlists, search, filters, and listening history.
* Optional lyrics, artwork, and metadata retrieval.
* Intelligent local music collections and recommendations.
* Smooth, modern, animated desktop UI.
* Strong offline functionality.
* Privacy-conscious local storage.
* Reliable operation on Windows, Linux, and macOS.

The application must remain useful without an internet connection.

Do not require users to create accounts or upload their music to external servers.

Prioritize audio correctness, stability, performance, usability, and maintainability over unnecessary features.

Use the relevant FFmpeg libraries for supported demuxing, decoding, and audio-format conversion.

## Testing

Use:

* GoogleTest for suitable C++ unit and integration tests.
* Qt Test for Qt-specific behavior.

## Audio Output

Design an independent audio-output interface with platform-specific implementations.

Windows:

* WASAPI.
* Exclusive output where supported.
* Shared output as an appropriate fallback.

Linux:

* PipeWire and/or ALSA, based on the available environment and implementation requirements.
* Handle device capabilities and audio-server availability.

macOS:

* Core Audio.
* Device configuration and output-mode reporting where supported.

Do not assume Qt Multimedia alone provides all the capabilities required for exclusive-mode or bit-perfect playback.

## Other Technologies

* FFT-based processing for audio visualization.
* Asynchronous tasks for library scanning and metadata retrieval.
* Git for version control.
* Platform-appropriate packaging tools for releases.

Avoid introducing additional dependencies without a clear technical reason.

# 6. AUDIOPHILE MODE

Implement a dedicated audiophile configuration system.

## Bit-Perfect Playback

Provide bit-perfect output where supported and verifiable.

Requirements:

* Preserve the decoded sample values through the output pipeline when bit-perfect mode is active.
* Avoid resampling when it would alter the intended signal.
* Avoid DSP, software gain, normalization, or crossfade operations that modify the samples.
* Use compatible device formats and output modes.
* Implement exclusive output where supported.
* Detect incompatible settings.
* Explain why bit-perfect playback may be unavailable.
* Distinguish verified, unavailable, and unknown output status.

Never label playback bit-perfect simply because the source is FLAC or another lossless format.

A lossless source can still be modified by the playback pipeline.

The application must accurately report when the current configuration cannot guarantee bit-perfect output.

## Output Configuration

Where platform APIs expose the information, display:

* Selected output device.
* Active backend.
* Source sample rate.
* Source bit depth when known.
* Source channel count.
* Output sample rate.
* Output sample representation or bit depth where known.
* Output channel configuration.
* Resampling status.
* DSP status.
* Exclusive/shared output status.
* Current capability or verification limitations.

Clearly distinguish source-file properties from the active output pipeline.

Do not fabricate unavailable hardware information.

## Resampling

Provide configurable resampling where supported.

Requirements:

* Select appropriate output rates.
* Avoid unnecessary conversion.
* Handle unsupported device configurations.
* Keep the output stable when switching rates.
* Test conversion accuracy using known signals.

## Equalizer and DSP

Implement:

* 10-band graphic EQ.
* 31-band graphic EQ.
* Parametric EQ.
* Preamp.
* User-defined presets.
* ReplayGain.
* Loudness normalization.
* Clipping prevention.
* Stereo balance.
* Channel controls.
* Optional crossfeed.
* Optional stereo enhancement.

Requirements:

* Stable filter implementations.
* Safe parameter ranges.
* No unexpected clipping.
* Correct handling of sample formats and channel layouts.
* Unit tests for important DSP algorithms.
* Clearly indicate when DSP disables bit-perfect output.

Use a modular processing graph that can bypass processing when appropriate.
